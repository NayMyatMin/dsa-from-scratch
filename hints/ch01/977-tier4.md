# 977. Squares of a Sorted Array — Tier 4 (full strategy)

Preallocate the result — `result = [0] * len(nums)` — and fill it **back to front**, from index
`n - 1` down to `0`, as the two pointers move inward. Each step writes exactly one slot, so the
loop runs n times, one comparison each. O(n) time, O(n) output and no extra working space.

Choose it because it says the output size up front and every step writes exactly one slot, which
is easy to read and easy to prove right — **not** because it is faster. It isn't.

## What the two write forms actually cost

The alternative is to append in descending order and reverse at the end. Also O(n). Measured at
n = 100,000 on this machine (CPython 3.14.4, best of 15–25 timed runs, repeated across sessions),
comparing two full solutions that are *identical* except for the write form — `result.append(v)`
versus `result[i] = v; i -= 1` — append-then-`.reverse()` came out ahead every single time, by
6% to 17% depending on the run. The preallocated twin was never the faster of the pair.

`.reverse()` is a second pass, but it is an in-place pass at C speed over a list that is already
the right size, and it costs about what the extra index bookkeeping costs the preallocated loop.
Stripped of the algorithm entirely, just building a 100,000-element list, `[0]*n` with `r[i] = i`
and `append` with `.reverse()` finish within a few percent of each other and trade places between
runs — a dead heat.

Peak memory is a dead heat too. `tracemalloc` over the full solution at n = 100,000, reproducing
to the byte across runs:

| variant | peak |
|---|---|
| preallocate, fill backwards | 3,991,488 B |
| append + `.reverse()` | 3,992,416 B |
| append + `[::-1]` | 4,792,416 B |

928 bytes separate the first two — that is the list's over-allocation slack, nothing more.

## The one variant that does measure worse

`[::-1]` materialises a whole second list. That is the +20% peak in the table above, and on the
bare list-building benchmark it runs 5–13% slower than `.reverse()` in every run. `.reverse()`
gets you the same result in place, without the copy. So the thing to avoid is not appending — it
is the slice.

## Elsewhere in the loop

Compare `abs(nums[left])` against `abs(nums[right])`, or compare the squares directly. Both work.
One of them does less arithmetic per iteration.

There is also a "find where the sign flips, then merge the two halves like the merge step of
mergesort" solution. Same O(n), and it's the more general idea — but it needs a binary search or a
scan for the pivot and two pointers moving outward. Worth writing after the first version, because
the merge pattern comes back repeatedly in this card.
