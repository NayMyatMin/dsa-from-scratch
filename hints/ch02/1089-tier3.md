# 1089. Duplicate Zeros — Tier 3 (approach)

Two families. The problem is really asking for the second.

## Give the write a source it cannot corrupt

Snapshot the array first, then walk the snapshot and write into `arr`. Reads and writes no longer
touch the same storage, so nothing can be clobbered and a single left-to-right pass works. O(n)
time, O(n) extra space, and it is still in place in the sense the problem means: the object handed
to you is the one holding the answer at the end.

Two Python details bite here, and they bite in either family:

```python
def rebind(arr):
    arr = [0, 0, 0]

readings = [4, 9, 7]
rebind(readings)
print(readings)
# -> [4, 9, 7]

prices = [4, 9, 7]
same = id(prices)
prices[:] = [4, 9, 7, 5]
print(id(prices) == same, len(prices))
# -> True 4
```

Assigning to the bare name changes nothing the caller can see. Assigning to the full slice does
mutate the original object — and will resize it just as happily, which the fixed-length rule
forbids.

## Refuse the extra memory

Without a snapshot, `arr` is source and destination at once, so every slot you write into has to be
one whose current value you are never going to read again. **That is a constraint on the order of
the writes, and it is satisfiable.** Finding the order is the problem.

This family needs one more thing. Tier 2 said a destination is a fact about a stretch of the array
rather than about one element — and a stretch is something you can measure, at the price of a pass
of its own. Expect two passes, and decide what the first one is for.

Then there is the far end, where values fall off. Work out on paper what should happen to a zero
whose second copy would land exactly one slot past the last index, before you write code that has
to survive it.

A third thing people reach for is `insert` for the extra zero and `pop` for the overflow. The
docstring rules it out; Tier 4 has the measured reason it deserves ruling out anyway.

> **The official hints, verbatim:** "This is a great introductory problem for understanding and
> working with the concept of in-place operations. The problem statement clearly states that we are
> to modify the array in-place. That does not mean we cannot use another array. We just don't have

> only reason the problem statement allows you to make modifications in place is that it hints at

>
> Those are this tier's two families, arriving one at a time — the first grants the snapshot, the
> second takes it back. Neither says anything about how the second family works.
