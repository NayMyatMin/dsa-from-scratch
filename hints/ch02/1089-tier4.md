# 1089. Duplicate Zeros — Tier 4 (full strategy)

## Count first, then imagine the room you do not have

Count the zeros: `z = arr.count(0)`. Now picture the array that would have existed if there had been
space for everything — length `n + z`, every zero doubled, nothing discarded. For
`[1, 0, 2, 3, 0, 4, 5, 0]` that is eleven slots reading `1 0 0 2 3 0 0 4 5 0 0`. **The first `n` of
those slots are the answer**; the tail beyond them is exactly the part that falls off the end.

You never build it. You only need the index arithmetic it implies. Carry two indexes: a read index
`i` stepping down from `n - 1` through the real array, and a write index `j` stepping down from
`n + z - 1` through the imagined one. At each step `arr[i]` is written at `j`, and if `arr[i]` is a
zero it is written a second time one slot further down. A write happens only when `j` is an index
the real array actually has — `j < n` — and anything aimed past that is a value that fell off, so
it is simply not written.

## Why walking down is safe

`j - i` is exactly the number of zeros in `arr[0:i+1]`. It starts at `z` and drops by one each time
the read index passes a zero, so it never goes negative: **`j >= i` at every step, on every input.**
Checked exhaustively over all 32,766 zero/one arrays of length 1 through 14 — not one step has
`j < i`, and both indexes finish on `-1` together.

That inequality is the correctness argument. Every write lands at or to the right of the element
just read, and everything to the right of `i` has already been read. The unread part is `arr[0:i]`,
and the write index never reaches into it.

## The end of the array is not a special case

The `j < n` test is the entire edge-case handling, truncated pairs included. On `[1, 2, 3, 0]` the
final zero gets its first copy written and its twin discarded, and the array comes back
`[1, 2, 3, 0]`, unchanged. Take the test out and the very first write on
`[1, 0, 2, 3, 0, 4, 5, 0]` raises `IndexError: list assignment index out of range`, because `j`
starts at 10 on an array of eight.

## Complexity, and what it actually buys

O(n) time — one counting pass, then one pass in which each element is read once and written at most
twice — and O(1) extra space. `tracemalloc` over the whole routine at n = 10,000, five runs of each
and identical every time: **0 bytes** peak for this version, **80,000 bytes** for a version that
snapshots with `arr[:]`, which is 10,000 slots at eight bytes each. (Driving the walk with `range`
rather than a counter shows 40 bytes on the first traced run and 0 on every one after — a single
range object, a fixed cost that does not grow with n.)

The O(1) version is not the fast one, and that is worth being honest about. Timed at n = 10,000 with
about 10% zeros, best of 9, with the cost of copying the input subtracted from both: the snapshot
version won every single run. Written to the same shape — one `for` loop apiece — the gap measured
1.57x, 1.55x and 1.57x over three rounds. A snapshot that builds its result with `append` and
assigns it back is quicker still, 2.2x to 2.3x, and peaks at 255,808 bytes doing it. Choose the
O(1) version because the memory bound is the exercise, not because it wins a stopwatch.

`arr.count(0)` is the right way to run the first pass, though the margin is narrower than it looks:
against a hand-written `for` loop over the same 10,000 elements it came out 1.19x–1.20x quicker,
same ordering on three independent runs (54.3–54.5 us against 64.8–65.1 us here). Use it because it
states its intent in one line. That pass is between a sixth and a fifth of the routine's total —
15.6% of the counter-driven walk, 18.4% of the `range`-driven one.

## Why `insert` and `pop` is the wrong shape

`arr.insert(i, 0)` does not make room for free. It slides every element from `i` onward one slot
along, so what it costs depends on how much array lies to the right of `i`:

```python
import timeit

setup = "b = [0] * 10_000"
front = min(timeit.repeat("b.insert(0, 0); b.pop()", setup, number=20_000, repeat=7)) / 20_000
back = min(timeit.repeat("b.insert(9_999, 0); b.pop()", setup, number=20_000, repeat=7)) / 20_000
print(round(front * 1e6, 2), "us to insert at the front")
print(round(back * 1e6, 3), "us to insert one slot from the back")
# -> 2.85 us to insert at the front
# -> 0.019 us to insert one slot from the back
```

Two orders of magnitude apart, and the ordering never wobbles: across eight runs of that block the
ratio landed between 139x and 160x. Do that once per zero and the routine is O(n·z), which on an
array of nothing but zeros is quadratic. Measured on all-zero inputs from n = 625 upward, each
doubling of n multiplied the insert-and-pop time by 3.34, 3.65, 3.81 and 3.90 — the 4x of a
quadratic, closing in from below — while the two-pass routine multiplied by 2.06, 2.03, 2.02 and
2.04, which is linear. At n = 10,000 all zeros that is about 7.1 ms against 0.32–0.36 ms depending
on how its loop is written, 20x to 22x apart.

The sliding is a memmove at C speed, which is why 10,000 elements costs milliseconds rather than
seconds — and that speed is exactly why a wall clock cannot referee this. In
`tests/ch02/test_p01_duplicate_zeros.py`, `test_large_input` allows 2.0 s for 25 passes over 10^4
zeros; the insert-and-pop version finishes them in 0.179 s, comfortably inside the budget.
`test_does_not_grow_quadratically` is the guard that sees what the budget cannot. From n = 10^4 to
8x10^4 on all zeros, insert-and-pop measured 63.5x while the two-pass routine measured 8.0x, against
a ceiling of 20.0. Beyond the shape being wrong, the docstring rules `insert` and `pop` out one by
one for a separate reason: each of them changes the length.

> **The official hint, verbatim:** "If we had enough space available, we would be able to
> accommodate all the elements properly. The new length would be the original length of the array
> plus the number of zeros. Can we use this information somehow to solve the problem?"
>
> That one is genuinely good — it is this tier's first section in two sentences. It stops just short
> of saying which direction to walk, which is the only part that is hard.
