# 283. Move Zeroes — Tier 4 (full strategy)

## One walk, one write index

Keep a single integer beside the list — call it the write index — starting at 0. It always means the
same thing: *the position the next surviving element belongs in*. Walk the list by index from 0 to
`len(nums) - 1`. **At each position, if the element there is not 0, write it to the write index and
advance the write index by one; if it is 0, do nothing at all and move on.** That is the entire first
phase, and it is one `if` inside one loop.

When the walk ends, the write index is no longer a position — it is a count. It advanced exactly
once per surviving element, so it holds how many there are, and Tier 2's arithmetic says those
survivors now occupy indices 0 through one less than it, in the order they arrived. **Second phase:
write 0 into every position from the write index to the end of the list.** There are `len(nums)`
minus the write index of them, which is the number of zeros the input contained, and you never had to
count those separately.

Then return nothing. The signature says `None` and the suite checks it: a correct rewrite of `nums`
followed by `return nums` fails here, and it fails with a message saying so, because that is the
contract 1299 next door uses and not this one.

You can run the first phase either way. `for x in nums` is legal even though the loop writes into
`nums` as it goes: the length never moves and every write lands at or behind the position just handed
to you, so nothing the iterator has yet to reach is disturbed — chapter 3 section 7's hazard is a
walk over a list whose *length* changes underneath it, and nothing here changes it. That spelling is
wrong on 0 of the 5,460 lists of length 1 to 6 drawn from `{0, 1, 2, -1}`, and it is the quicker of
the two: over six rounds on six zero patterns at n = 10^4 it cost between 0.66x and 0.73x what the
indexed form cost, on every one of the thirty-six readings, which is one subscript per element
removed. What an index buys is the read position itself — the invariant below is stated in terms of
it, and the write-skipping variant in the follow-up has to compare against it. `enumerate(nums)`
hands you both.

## Why writing forward is safe

The concern is obvious once you see it: you are writing into a list you have not finished reading.
The answer is an invariant, and it is worth stating rather than trusting.

At the top of every iteration the write index is less than or equal to the read index. It starts
equal, at 0, and it advances at most once per step of the read index — so it can fall behind and can
never get ahead. Checked over every list of length 1 to 6 drawn from `{0, 1, 2, -1}`, all 5,460 of
them, it was violated 0 times.

That is the whole safety argument. The slot you write is one the read index has already passed, so
whatever was in it has been dealt with: either a 0, which the answer needs no record of beyond its
count, or a survivor already copied further left. When the two indices are equal the write puts an
element back where it already was, which is harmless. Tier 2's sweep found the same fact from the
other end — no survivor ever ends up to the right of where it started.

The invariant that makes it *correct*, as opposed to merely safe, is the one to check your loop
against: after the step that reads index `r`, the first `w` positions hold exactly the survivors
among the first `r + 1`, in the order they appeared. It is true before the first step, both branches
preserve it, and at the end it says the survivors are in place in order — which with the second
phase is the statement transcribed.

## What falls out rather than being handled

There is no length branch anywhere and no special case for the ends. A one-element list runs the
first phase once and the second phase either zero or one time. A list with no zeros never advances
the two indices apart, so every write puts an element back where it was and the second phase does not
run — the list comes out unchanged, which is the right answer. A list of nothing but zeros never
advances the write index, so the second phase overwrites every position with the 0 already sitting in
it. Both are correct without being noticed.

The answer being the input is not rare and is worth expecting: 1,635 of those 5,460 lists are
already exactly what a correct solution must leave behind.

## Complexity, and what it actually costs

The first phase runs `n` iterations and the second runs `n` minus the number of survivors, so no
index is visited more than twice and the total is at most `2n` steps. Every step is an indexed read,
an indexed write, a comparison against 0 and an integer increment, and chapter 1 section 8's table
charges `nums[i]` and `nums[i] = v` O(1) each — one bounds check and one pointer offset, on a
four-element list and on a four-million-element one alike. **O(n) time, O(1) extra space.**

The space claim is measurable and was measured: `tracemalloc` around the whole routine, forty traced
passes on each of six zero patterns at each of two sizes. **Peak 0 bytes on 237 or more of every 240
passes, at n = 10^4 and at n = 10^5 alike.** The three exceptions at n = 10^4 read 96, 104 and 128
bytes and the two at n = 10^5 read 96 and 128: a figure that does not move with `n` is what a
constant looks like when you measure one. Nothing is allocated for the data because every write
lands in a slot that already exists — chapter 2 section 5's length-preserving property, which
chapter 3 section 6 weighs in bytes against the alternative.

Against the suite's growth guard, on this repo's interpreter, CPython 3.14.4: eight times the input
bought about eight times the work. Six readings on each of six zero patterns — none, all, half
scattered, a block at each end, and alternating — at n = 4,000 against n = 32,000, and all 36 landed
between 7.6x and 8.4x. The guard's ceiling is 25x.

## The follow-up: how many writes

"Could you minimize the total number of operations done" is not graded, and it is the most
interesting question left. Counted at n = 10^4 on fixed shapes, so the figures reproduce exactly:

The version above performs **exactly `n` writes on every input, always** — one per survivor in the
first phase and one per zero in the second, and those add to `n` by construction. Over all 5,460
short lists it deviated from `n` 0 times. That is 10,000 writes at the ceiling whatever the input
looks like, including on a list that was already the answer.

Skipping the write when the two indices are equal, and skipping a 0 written onto a 0, drops it to 0
writes on a list with no zeros, 0 on a list of nothing but zeros, 0 on a list already in the answer,
7,500 where zeros and values alternate, and 10,000 on a list whose zeros are all at the front — that
last one being the input where every survivor genuinely has to move. On writes it is never worse and
often much better, and the comparison it pays per element is not free: measured at n = 10^4 over six
rounds it cost between 1.08x and 1.20x the plain version on four of the six zero patterns, came out
level with it on the shape whose answer is already the input, at 1.01x to 1.02x, and cost less than
it only on the one with no zeros in it, at 0.93x to 0.94x. **The follow-up's metric is operations,
and the clock is under no obligation to agree with it.**

Exchanging the two positions instead of copying forward is the other variant, and it is worse at
this. A swap is two writes, so it costs twice the number of survivors: 20,000 on a list with no zeros
at all against the copy-forward version's 10,000, and 19,998 where the single zero sits at index 0.
The same equal-indices test rescues it — 0 on a list with no zeros — but where the indices have come
apart it stays at two writes per survivor, 10,000 on the alternating shape against the skipping
copy-forward version's 7,500. What the swap buys is that there is no second phase at all: the zeros
are carried to the back by the exchanges themselves. Shorter program, more writes.

## The approaches not taken

**Build the survivors elsewhere and write them back.** The first official hint's starting point, and
the way the reference the suite grades against is written, because being obviously right mattered
more there than being in place. It is also the quickest of everything here: at n = 10^4 over
thirty-six readings on six zero patterns the walk cost between 1.9x and 2.3x what this did, the
ordering holding on all thirty-six. Not because one route is C and the other is not — both run
bytecode per element — but because the walk reaches every element through a subscript twice, an
access Tier 3 measures at 3.6x to 4.8x the cost of being handed the element. What it spends is
memory: peak traced 160,000 bytes at n = 10^4 on a list of nothing but zeros, 245,120 on a list with
none, 201,824 to 201,920 on the mixed patterns, against 0 for the walk — and about ten times each of
those at n = 10^5, which is what "grows with the list" looks like when you measure it. Nothing in
this suite measures space, and the statement's "without making a copy" is the one requirement here
that nothing can enforce.

**A stable sort with a key.** Falsy for survivors, truthy for zeros; stability keeps the survivors in
order. Wrong on 0 of the 5,460 short lists, O(n log n), and peak traced 80,168 bytes at n = 10^4
where the zeros form one block, 120,168 and 120,200 where they are scattered or alternate with
values — the extra 40,000-odd being `n / 2` pointers of merge buffer. Timed against it over those
same thirty-six readings the walk cost between 0.54x and 1.02x, the sort's margin tracking how much
the keys interleave and not the length.

**Lifting each zero out and putting a zero on the end.** The shape the growth guard exists to catch.
It is genuinely in place — peak traced 0 bytes on 238 of 240 passes at n = 10^4, the walk's reading
to within a pass — which is the lesson in it: constant extra space says nothing about time. Removing
an element from the middle slides the whole tail one slot left, so one removal per zero is a
full-length move inside a full-length loop. Eight times the input cost it between 54x and 100x on
the five patterns that contain zeros. On the one that contains none it cost 8.0x, and at n = 10^4 it
was measured at 0.86x the walk — not merely inside the correct band but *faster than the right
answer*, because a list with no zeros gives it nothing to lift out. **That ordering depends on there
being zeros**, which is why more than one pattern gets timed.

**Swapping each zero with something from the far end.** One pass, no allocation, every zero at the
back, and wrong: it does not preserve the order of what is left. Over the 5,460 short lists it is
wrong on 2,502, its smallest failure `[0, 1, 2]`, and on all 2,502 the zeros are exactly where they
belong. `[0, 1, 0, 3, 12]` comes out `[12, 1, 3, 0, 0]`.

## Before you call it done

Run `uv run pytest tests/ch05/test_p02_move_zeroes.py`, then check by hand: `[0]`, `[1]`, `[0, 0]`,
`[1, 2, 3]`, `[1, 0, 0]`, `[0, 0, 1]`, `[0, 1, 0, 3, 12]`, `[1, 0, 2, 0, 3]`, `[0, 0, 0, 5]` and
`[2147483647, 0, -2147483648]`. Exactly five of those ten come back exactly as they went in, and
`[0, 0, 1]` and `[1, 0, 0]` are the pair worth staring at — same three values, one of them is
already the answer and the other is not.

Then confirm three things that have nothing to do with zeros. The call returns `None`. `len(nums)`
is what it was. And the caller's own list is the one that changed — rebinding `nums` inside the
method delivers a correct answer to an address nobody reads, and the suite reports that as nothing
having been written into `nums` at all.
