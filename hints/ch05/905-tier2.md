# 905. Sort Array By Parity — Tier 2 (observation)

One sentence in the statement changes what this problem is, and it reads like politeness rather than
a rule: **return any array that satisfies this condition.** Take it literally. It is not saying that
several answers are close enough to be waved through. It is saying the question has many correct
answers, all worth the same, and you may produce whichever one is cheapest for you to produce.

## How much freedom that is, counted

The grading rule fits in four lines, and once it is written down every input's accepted answers can
be enumerated by brute force:

```python
from itertools import permutations


def accepted(nums, answer):
    """The whole grading rule: the same values, and no odd value in front of an even one."""
    if sorted(answer) != sorted(nums):
        return False
    parity = [x % 2 for x in answer]
    return all(p <= q for p, q in zip(parity, parity[1:]))


def how_many(nums):
    """How many distinct lists that rule accepts for this input."""
    return len({p for p in permutations(nums) if accepted(nums, p)})


print(how_many([1, 2]), how_many([1, 3]), how_many([1, 3, 5, 2]), how_many([3, 1, 2, 4]))
# -> 1 2 6 4
print(how_many([2, 1, 2, 1, 2, 1]), how_many([0]))
# -> 1 1
```

`[1, 2]` has one accepted answer and `[1, 3]` has two, and neither the length nor the size of the
values explains it: two odd numbers sit in the same group, and inside a group nothing is ordered at
all. `[1, 3, 5, 2]` has six for that reason — one even value, then three odds free to appear in any
of the `3!` orders. `[2, 1, 2, 1, 2, 1]` has thirty-six orderings and one accepted *list*, because
its evens are all the same value and rearranging equal values changes nothing anybody can see.

Over all 5,460 lists of length 1 to 6 drawn from `{0, 1, 2, 3}` — the exhaustive set the suite
grades short inputs against — the number of distinct accepted answers ran from 1 to 20, and 768 of
those lists were already an accepted answer exactly as they arrived. At the constraint ceiling the
count stops being printable: 5,000 distinct values, half of them even, admit `2500! * 2500!`
accepted answers, a number with 14,823 decimal digits. Every one of them scores the same.

## The shape of every accepted answer is fixed by one number

Throw the values away and keep one character per element, and the rule becomes a statement about a
string:

```python
def pattern(a):
    """One character per element: E for even, O for odd. Values thrown away."""
    return "".join("E" if x % 2 == 0 else "O" for x in a)


for a in ([3, 1, 2, 4], [2, 4, 1, 3], [2, 1, 4, 3], [1, 0, 0, 3, 0], [0]):
    print(f"{str(a):18} {pattern(a)!r}")
# -> [3, 1, 2, 4]       'OOEE'
# -> [2, 4, 1, 3]       'EEOO'
# -> [2, 1, 4, 3]       'EOEO'
# -> [1, 0, 0, 3, 0]    'OEEOE'
# -> [0]                'E'
```

An accepted answer's pattern is some run of `E`s followed by some run of `O`s and never anything
else: one boundary, and no exceptions on either side of it. The length of the first run is not yours
to pick either — it is however many even values the input held, since you may only rearrange what
you were handed. Checked exhaustively over those same 5,460 lists: for every one of them, every
accepted answer shares the single pattern `"E" * k + "O" * (n - k)`, where `k` is the count of
evens. Not one input had accepted answers with two different patterns.

**So exactly one number in this problem is not yours to choose, and past knowing which side of that
boundary a value belongs on, nothing about where any element ends up is part of the answer.**

## Nothing is ever compared with anything else

Look at what decides an element's group: the element. `7` is odd in every list it will ever appear
in, and no other element has a vote. Ordering by value is a different situation, where where an
element belongs depends on every other element and cannot be settled by looking at it alone — which
is why sorting by value here is not a near miss but an answer to another question. The suite rejects
`[1, 2, 3, 4]` for the input `[3, 1, 2, 4]` and is right to: 3 is less than 4 and it is still odd.

Every element's parity does have to be looked at once, because flipping any single element from even
to odd moves it across the boundary and changes the answer. That is the floor — `n` parity tests —
and the docstring's `O(n)` target is that floor rather than an ambition.

## The cost is in the moves, not in the tests

The parity tests are cheap and there are `n` of them. What separates solutions is what happens to a
value once its parity is known, and one natural-sounding answer is expensive in a way that hides:
moving it to the front or the back of a list as a *list operation*. Chapter 1 section 8 prices
those — `insert(i, x)` is O(n − i) because it moves every element from `i` onward one slot to the
right, and `pop(i)` and `del` do the same work in reverse. Building a 5,000-element list by putting
each value at the front therefore shifts

```python
print(sum(range(5000)))
# -> 12497500
```

pointers, twelve and a half million of them, to place five thousand values. Measured on this repo's
interpreter, CPython 3.14.4, the two loops timed in alternation so that neither gets a quiet stretch
of machine to itself: 5,000 `insert(0, x)` calls took 3.6 to 3.8 ms and 5,000 `append` calls took
0.055 to 0.059 ms, the first between 62x and 66x the second. Double the input and the first roughly
quadruples while the second roughly doubles — over two runs at 5,000, 10,000, 20,000 and 40,000
elements, the front-insert loop multiplied by 3.88 to 4.11 per doubling and the append loop by 1.88
to 2.21.

**One input will not tell you which of your loops is doing that.** The problem is symmetrical: one
group has to finish in front and the other behind, so a route that carries evens forwards pays that
cost once per even and pays nothing whatever on a list holding no evens. Measured at n = 5,000, per
call, over three runs: a route that inserts each even at the front of a list cost 0.109 to 0.114 ms
on a list of nothing but odd values and 3.66 to 3.67 ms on a list of nothing but even values, from
the same code — between 32x and 34x the price for the same n, decided by nothing but which parity
the input was made of. The mirror route, carrying each odd to the back one at a time, measured
0.110 to 0.111 ms on the all-even list and 2.06 ms on the all-odd one. Either input on its own would
report one of those two routes as free, which is why `test_does_not_grow_quadratically` times four
shapes rather than one.

*How* the values get onto their sides of the boundary is the one thing this tier deliberately does
not answer. Work at it yourself first. You now know the shape of the answer, that no comparison
between two elements is needed to reach it, and which operation to keep out of the loop.
