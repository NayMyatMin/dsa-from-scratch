# 1299. Replace Elements with Greatest Element on Right Side — Tier 2 (observation)

"The greatest element among the elements to its right" describes one position's answer completely,
and read `n` times over it looks like `n` separate searches. It is not `n` searches. **The
collections those searches would run over are nested, each one the next with a single element added
in front, so an answer and the answer one place to its right differ by exactly one comparison.** The
elements to the right of index `i` are the element at `i + 1` together with the elements to the
right of `i + 1`. The greatest of that is the greater of two numbers you would already be holding:
the element at `i + 1`, and the answer at `i + 1`.

```python
from itertools import product


def answers(arr):
    """The statement transcribed: every position takes the greatest of the elements to its right."""
    n = len(arr)
    return [max(arr[i + 1:]) if i + 1 < n else -1 for i in range(n)]


print(answers([17, 18, 5, 4, 6, 1]))
# -> [18, 6, 6, 6, 1, -1]

checked = broken = 0
for n in range(1, 7):
    for tup in product((1, 2, 3), repeat=n):
        arr, ans = list(tup), answers(list(tup))
        for i in range(n - 1):
            checked += 1
            broken += ans[i] != max(arr[i + 1], ans[i + 1])

print(checked, "positions over 1,092 lists,", broken, "where that failed")
# -> 4923 positions over 1,092 lists, 0 where that failed
```

Every list of length 1 to 6 over `{1, 2, 3}` — three values being enough to make a neighbour larger,
smaller or equal, and exhaustive meaning no arrangement of them is left to chance — and the
two-argument version never once disagreed with the slice. The last position is the one that does not
participate: it has nothing to its right, so the statement does not derive its answer at all, it
fixes it at `-1`. That is the end the nesting is anchored to, not an exception bolted onto it.

A consequence worth having in front of you before you write anything. Since each answer is the
greater of the next answer and one more element, no answer can be smaller than the one to its right,
so **the finished list is always non-increasing** — over those same 1,092 lists, including the final
`-1`, there was not one exception. But *how often it actually changes* is a property of the input
and of nothing else:

```python
def derived(arr):
    """Every answer the statement derives, which is all of them but the last."""
    return [max(arr[i + 1:]) for i in range(len(arr) - 1)]


def changes(arr):
    """How many times an answer differs from the answer one place to its right."""
    ans = derived(arr)
    return sum(x != y for x, y in zip(ans, ans[1:]))


for arr in ([6, 5, 4, 3, 2, 1], [17, 18, 5, 4, 6, 1], [7, 7, 7, 7, 7, 7], [1, 2, 3, 4, 5, 6]):
    print(arr, "->", derived(arr) + [-1], changes(arr), "changes")
# -> [6, 5, 4, 3, 2, 1] -> [5, 4, 3, 2, 1, -1] 4 changes
# -> [17, 18, 5, 4, 6, 1] -> [18, 6, 6, 6, 1, -1] 2 changes
# -> [7, 7, 7, 7, 7, 7] -> [7, 7, 7, 7, 7, -1] 0 changes
# -> [1, 2, 3, 4, 5, 6] -> [6, 6, 6, 6, 6, -1] 0 changes
```

Nothing in the constraints says which of those you will be handed, and all four are legal. So a
solution whose cost depends on how often the answer changes is quick or hopeless depending on the
input, and testing it on one list tells you nothing about the other. That is not a hypothetical:
`tests/ch05/test_p01_replace_greatest_right.py` times its growth guard on five separate shapes, and
its docstring marks, shape by shape, which wrong solutions each one is blind to.

Now the reason any of this matters, which is what the nesting saves you from. `max(arr[i + 1:])`
reads `n - 1 - i` elements and copies them into a fresh list first — `notes/01_introduction.md`
section 8 prices `nums[a:b]` at O(b − a) in time *and* space. Taken once per position, that is the
same handful of facts re-established from scratch at every step:

```python
for n in (500, 1000, 5000):
    print(f"{n:5,} answers  {n * (n - 1) // 2:12,} element readings")
# ->   500 answers       124,750 element readings
# -> 1,000 answers       499,500 element readings
# -> 5,000 answers    12,497,500 element readings
```

Five thousand answers, twelve and a half million readings: each answer arrived at by reading an
average of 2,499.5 elements when the observation above says one comparison would have done. Double
the input and the count multiplies by 4.00; take ten times the input and it multiplies by 100.18.
Measured on this repo's interpreter, CPython 3.14.4, at the constraint ceiling `n = 10^4`: one
`max()` over a slice per position took 412 to 470 ms per call across four shapes, against 0.140 to
0.195 ms for a pass doing a fixed amount of work per element — a ratio of between 2,225x and 2,996x,
three readings on each of the four shapes in each of two runs, the two routes timed one after the
other inside every round and the ordering never in doubt in any of them. The same
eight-times-the-input growth the suite measures came out between 63.09x and 67.60x for the slice
version and between 8.26x and 8.80x for the fixed-work one, against a ceiling of 25x. Both of the
suite's timing guards exist to say that out loud.

What this tier deliberately does not settle is how you evaluate that two-argument comparison inside
`arr` itself, which is where the answer has to end up. **`arr` is both the question and the answer
here**, and that is the whole of this chapter: every value you write into it destroys an element
some position was entitled to read. Every value except `arr[0]`, that is — nothing lies to the left
of index 0, so it is the one element no answer anywhere depends on. Work out which values you are
allowed to destroy, and when, before you write anything.
