# 283. Move Zeroes — Tier 2 (observation)

There is exactly one accepted answer per input, and the useful thing about it is not that it is
unique but that **every element's final position is decided by a count, not by a search.** Walk left
to right keeping a tally of the zeros you have passed. When you reach an element that survives, the
number of survivors already behind it is its destination index, and that number is its own index
minus the tally. Nothing about the values matters, nothing later in the list matters, and no element
has to be compared with any other.

```python
from itertools import product


def destinations(nums):
    """Every element that survives, as (where it starts, its value, where it has to end up)."""
    zeros, out = 0, []
    for i, x in enumerate(nums):
        if x == 0:
            zeros += 1
        else:
            out.append((i, x, i - zeros))
    return out


for nums in ([0, 1, 0, 3, 12], [1, 0, 2, 0, 3], [0, 0, 4], [7, 8, 9]):
    print(nums, destinations(nums))
# -> [0, 1, 0, 3, 12] [(1, 1, 0), (3, 3, 1), (4, 12, 2)]
# -> [1, 0, 2, 0, 3] [(0, 1, 0), (2, 2, 1), (4, 3, 2)]
# -> [0, 0, 4] [(2, 4, 0)]
# -> [7, 8, 9] [(0, 7, 0), (1, 8, 1), (2, 9, 2)]

lists = [list(t) for n in range(1, 7) for t in product((0, 1, 2, -1), repeat=n)]
not_its_rank = moves_right = 0
for nums in lists:
    for rank, (src, _value, dest) in enumerate(destinations(nums)):
        not_its_rank += dest != rank
        moves_right += dest > src
print(len(lists), not_its_rank, moves_right)
# -> 5460 0 0
```

Two facts came out of that sweep, over every list of length 1 to 6 drawn from `{0, 1, 2, -1}` — the
same exhaustive set the suite grades short inputs against. The first is the arithmetic restated:
a survivor's destination is always its rank among the survivors, 0 exceptions in 5,460 lists. The
second is the one to hold on to. **No surviving element ever ends up to the right of where it
started** — 0 exceptions again, and it could not be otherwise, since the tally of zeros passed is
never negative. Every element either stays where it is or moves left.

Where the survivors stop is the rest of the answer. If `k` of them survive they occupy indices `0`
through `k - 1`, so indices `k` through `n - 1` are exactly the positions left over, there are
`n - k` of them, and every one holds a `0`. You know that count without a second look at the input,
because it is the tally you were already keeping.

> **The official hints, verbatim.** There are two, and only the first belongs at this tier: "*In-place*
> means we should not be allocating any space for an extra array. But we are allowed to modify the
> existing array. However, as a first step, try coming up with a solution that makes use of
> additional space. For this problem as well, first apply the idea discussed using an additional
> array and the in-place solution will pop up eventually."
>
> The idea it points back at is the counting above, and the suggestion is a good one: assemble the
> survivors somewhere of your own, pad to length, and you have a working answer to compare against
> while you work on a better one. Be exact about what "in place" is worth here, though, because the
> hint overstates it. Nothing measures what you allocate. What is enforced is the object and its
> shape: the answer has to be in `nums` itself, `len(nums)` has to come out as it went in, and the
> method has to return `None`. A solution that builds the answer in a list of its own and then
> writes it into `nums` satisfies all three and passes. Allocating nothing is the better answer and
> the reason this chapter exists; it is not the condition for being right.

The two ways this problem goes wrong are worth naming before you spend an attempt on either.

**Reaching for an operation that closes a gap.** Every way of taking an element out of the middle of
a list slides the whole tail one slot left to fill the hole — chapter 1 section 8's table charges
`nums.pop(i)` and `del nums[i]` O(n − i) for exactly that. Doing one per zero puts a full-length
move inside a loop that already runs the length of the list. Counted rather than timed, so the
figures reproduce:

```python
def slides(nums):
    """Elements moved by lifting each zero out with pop() and putting a zero on the end."""
    nums, n, i, seen, moved = list(nums), len(nums), 0, 0, 0
    while i < n - seen:
        if nums[i] == 0:
            moved += len(nums) - i - 1   # pop(i) slides everything behind i one slot left
            nums.pop(i)
            nums.append(0)
            seen += 1
        else:
            i += 1
    return moved


for n in (1_000, 2_000, 4_000):
    print(n, slides([0] * n), slides([0 if i % 2 == 0 else 7 for i in range(n)]), slides([7] * n))
# -> 1000 999000 374750 0
# -> 2000 3998000 1499500 0
# -> 4000 15996000 5999000 0
```

Double the input and each of the first two columns quadruples. That is the growth guard's whole
subject, and the third column is why the suite times more than one shape: with no zeros in the list
there is nothing to lift out, this shape does no sliding at all, and it looks perfectly linear. The
clock agrees. Measured on this repo's interpreter, CPython 3.14.4, at n = 4,000 against n = 32,000,
six readings on each of six zero patterns — none, all, half scattered, a block at either end and
alternating — eight times the input cost this route between 54x and 100x on the five patterns that
contain zeros, and 8.0x on the one that contains none. That last shape is the trap: it grows
linearly, one call at n = 10^4 measured between 0.18 ms and 0.20 ms, and there is nothing in that
for a timing guard to catch. **The ordering depends entirely on there being zeros to move**, so a
solution timed only on a list without any has not been timed at all.

**Getting the zeros right and the order wrong.** Swapping each zero with something dragged in from
the far end puts every zero at the back in one pass, and scrambles what is left: `[0, 1, 0, 3, 12]`
comes out `[12, 1, 3, 0, 0]`. Over those same 5,460 lists that shape is wrong on 2,502 of them, and
here is the part worth sitting with — on all 2,502, every zero is exactly where it belongs. Its
smallest failure is three elements long, `[0, 1, 2]`. A check that only asked where the zeros went
would call every one of those correct, which is why the suite compares the whole list, position by
position, against an answer computed before your code ran.

How to get the survivors into their known destinations without a second list is the question this
tier stops in front of. Work at it yourself first.
