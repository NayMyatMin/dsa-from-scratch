# 1346. Check If N and Its Double Exist — Tier 4 (full strategy)

## One walk, one set, two questions

Keep a `set` that starts empty and holds the values you have already walked past. Take the elements
of `arr` in order and call the one in hand `x`. Ask that set two things: does it hold `2 * x`, and
does it hold half of `x`. Either yes is a finished answer — return `True` immediately. Only after
both questions have been asked do you put `x` into the set. When the walk ends with no yes, return
`False`.

The order of those two steps is the whole of the `i != j` requirement. Everything in the set sits at
a position strictly before the one you are standing on, so any match it reports is at a different
position, by construction — no counting of zeros, no comparing of indices, nothing. Add `x` before
asking instead of after and you hand it permission to match itself, which is wrong on 456 of the
3,900 lists of length 2 to 5 drawn from `{-2, -1, 0, 1, 2}`. Every one of those 456 is an invented
pair rather than a missed one, and every one of them holds a zero — because **`x == 2 * x` has
exactly one solution, so zero is the only value that can be its own partner.**

Two questions and not one, because a pair is `a` and `2 * a` and the walk meets them in whichever
order the input chose. Whichever arrives second is the one that finds the pair, and it is sometimes
the double and sometimes the half. Asking only about doubles misses 724 of those same 3,900 lists,
all of them missed pairs, the smallest being the two-element `[-1, -2]` and `[1, 2]`.

## Halving, which is the one place this problem bites

> **The third official hint, verbatim:** "Also check if we have seen `arr[i] / 2` in case
> `arr[i] % 2 == 0`."

The second half of that sentence reads as a correctness condition. Whether it is one depends
entirely on which division you write, and the hint does not say. Ask it one element at a time — an
`x`, a set of the values standing behind it, and the candidate arithmetics side by side:

```python
from itertools import combinations

LO, HI = -4, 4
values = range(LO, HI + 1)
seen_sets = [frozenset(c) for r in (1, 2, 3) for c in combinations(values, r)]
questions = [(x, seen) for x in values for seen in seen_sets]


def truth(x, seen):                 # the statement, asked of one element against earlier values
    return any(y == 2 * x or x == 2 * y for y in seen)


def floor_half(x, seen):            # no parity guard, floor division
    return 2 * x in seen or x // 2 in seen


def true_half(x, seen):             # no parity guard, true division
    return 2 * x in seen or x / 2 in seen


def guarded(x, seen):               # the hint's condition, floor division
    return 2 * x in seen or (x % 2 == 0 and x // 2 in seen)


for name, candidate in (("floor  ", floor_half), ("true   ", true_half), ("guarded", guarded)):
    wrong = sum(1 for x, seen in questions if candidate(x, seen) != truth(x, seen))
    print(name, wrong, "wrong of", len(questions))
# -> floor   132 wrong of 1161
# -> true    0 wrong of 1161
# -> guarded 0 wrong of 1161
print(floor_half(1, {0}), truth(1, {0}))
# -> True False
print(-1 // 2, -3 // 2, 5 // 2)
# -> -1 -2 2
print(all((x / 2) == (x // 2) for x in range(-1000, 1001, 2)))
# -> True
```

`-1 // 2` is `-1` and `-3 // 2` is `-2`. Floor division on an odd number does not produce that
number's half; it produces a neighbouring integer that is very likely to be sitting in your data.
Standing on `1` with a `0` behind you is the whole failure in miniature: `1 // 2` is `0`, the set
says yes, and the statement says no. Unguarded that is 132 wrong of 1,161 here, and it survives
assembly into whole lists — the shortest inputs it gets wrong are two elements long, and over this
block's own `-4` to `4` there are exactly four of them: `[0, 1]`, which is that miniature written
out, plus `[-1, -1]`, `[-2, -3]` and `[1, 3]`. The statement answers False on all four, and across
the whole of `-1000` to `1000` there are 1,000 such pairs. With `%` used as the guard it is right on
all 1,161, because the two divisions agree exactly on every even value in the legal range, which the
last line of that block checks one by one.

True division needs no guard at all. `x / 2` on an odd `x` is a float ending in `.5`, no set of
integers contains one, and the query simply says no — the same sweep gives 0 wrong out of 1,161 for
a version with `/` and no parity test. So the hint's condition is a *correctness* requirement for
`//` and an *optimization* for `/`, and as an optimization it is not free:

```python
import timeit

odd = [2 * k + 1 for k in range(250)]        # 1, 3, ... 499
even = [4 * k + 2 for k in range(250)]       # 2, 6, ... 998
pool = set(range(-1000, 1001, 3))
for label, data in (("all odd ", odd), ("all even", even)):
    g = min(timeit.repeat(lambda: sum(1 for x in data if x % 2 == 0 and x // 2 in pool),
                          number=400, repeat=9)) / 400
    u = min(timeit.repeat(lambda: sum(1 for x in data if x / 2 in pool),
                          number=400, repeat=9)) / 400
    print(f"{label}  guarded {g * 1e6:5.1f} us   unguarded {u * 1e6:5.1f} us   {u / g:.2f}x")
# -> all odd   guarded   4.0 us   unguarded   5.3 us   1.31x
# -> all even  guarded   9.1 us   unguarded   7.5 us   0.82x
```

The guard skips a lookup for every odd element and adds a test to every even one. Which way that
lands depends on the data. Across fourteen runs the odd column stayed between 1.29x and 1.43x and
the even column between 0.78x and 0.83x, and neither ever crossed over: a win where odd values
dominate, a loss where they do not.

## Complexity

One pass, at most two constant-time queries and one insertion per element: **O(n) time.** The set is
the space, and it is bounded twice over — by `n`, and by the 2,001 legal values, so it cannot grow
past 2,001 entries however long `arr` gets. At the ceiling, five traced runs and identical every
time:

```python
import tracemalloc

worst = [2 * k + 1 for k in range(500)]
tracemalloc.start()
seen = set()
for x in worst:
    seen.add(x)
print(tracemalloc.get_traced_memory()[1], "bytes peak for the set alone")
tracemalloc.stop()
# -> 41176 bytes peak for the set alone
```

That is O(n) extra space, not O(1), and it is fine: the suite does not measure memory and says so.
Chapter 5 is where the space bound becomes the subject.

## The approaches not taken

Per call at `n = 500` on 500 odd values, so nothing exits early. Best of nine rounds:

| shape | ms per call | against the single pass |
|---|---|---|
| every pair, two loops | 4.827 | 197x to 232x |
| `2 * x in arr` inside one loop | 1.450 | 62x to 68x |
| `sorted(arr)` plus `bisect_left` | 0.042 | 1.78x to 1.98x |
| one pass, set of what you passed | 0.023 | 1.00x |
| set of the whole list, zero handled apart | 0.020 | 0.85x to 1.00x |

Absolute microseconds drift between runs, so the ratios are the column to read. Across sixteen
rounds the order of the top four rows never changed. The bottom two are a different matter: they
are close enough that the gap between them is the same size as the noise around it.

**A set of the whole list.** Never slower than the prefix set across those sixteen rounds and usually
a few per cent quicker, though one round came out level; it asks one question per element instead of
two — if `a` and `2 * a` are both present, then standing on `a` and asking for `2 * a` finds them,
whichever order they appear in. Checked exhaustively, a doubling-only sweep over a whole-list set
with the zero case handled separately is right on all 3,900 of the small lists. The cost is that
"handled separately" is now yours to write: zero is the one value whose presence in the set does not
prove a partner at another position, so it needs its own answer, and that is the failure Tier 2
measured at 456 cases.

**A sorted copy and `bisect_left`.** O(n log n), around twice the single pass at the ceiling, and it
carries no hash table. Worth reaching for when values are not hashable or when you need positions
rather than a yes/no. It inherits the zero question intact, and it needs the range-check-then-compare
guard from Tier 3, because the index it returns can be one past the end.

**Every pair.** Quadratic, and visibly so: doubling the input multiplied its time by 4.12, 4.03 and
4.12 from 500 to 4,000, against 1.91, 2.08 and 1.94 for the single pass. It is also, at this
problem's ceiling, an answer that runs in single-digit milliseconds and is accepted without
complaint. Prefer the single pass because it is the better piece of work, not because anything here
demands it.

Run `uv run pytest tests/ch04/test_p01_check_double_exists.py`, then check by hand: `[0, 3]` and
`[1, 0, 5]` are False, `[0, 0]` and `[3, 0, 0]` are True, `[-2, -4]` is True, and `[3, 1, 7, 11]` is

the return value alone; nothing you write into `arr` is ever read.
